## 3. Architecture and decisions

### Crates and responsibilities

- `nullamp-core`: pure, fully unit-tested logic. No I/O, so most behaviour is testable without hardware.
- `nullamp-audio`: the engine, behind a small command/event API with tokens.
- `nullamp-meta`, `nullamp-sysmedia`: one concern each.
- `nullamp-update`: copied from macsplorer's `update-check`. `check(url, current, user_agent)` runs `curl` (no TLS stack), reads GitHub's latest-release JSON or `{"version", "url"}`, and compares versions (pre-releases sort before releases). `Settings::update_url` (settings.json only) defaults to the GitHub latest release of `jbrunemann/nullamp`. `dialogs::check_for_updates` runs it on a helper thread and the result arrives as `DialogResult::UpdateChecked`. `cargo test -p nullamp-update -- --ignored` asks GitHub.
- `nullamp-artwork`: the cover of one track of a mix by artist and title. `find` asks Deezer's search, then iTunes Search (both keyless), with up to two queries each (the title without plain suffixes like "(Original Mix)", then the bare title), and `best` accepts a result only when one of its artists is one of ours and its bare title is ours; an exact version wins, and DJ-mix and various-artists releases lose. `download` fetches the image. Both run `curl` like `nullamp-update`. `cargo test -p nullamp-artwork -- --ignored` asks the services.
- `nullamp-shazam`: names the tracks of a mix with Shazam (section 7, "Identify with Shazam"). `signature` turns 16 kHz mono into the Shazam apps' signature, `recognise` posts one with `curl`, `clip_starts` places the clips, `agree` combines a track's answers into a `Verdict`. `cargo run --release -p nullamp-shazam --example identify -- MIX CUE` runs it against a cue sheet and compares titles.
- `nullamp-rekordbox`: read-only reader for rekordbox libraries. A USB export: tracks from `PIONEER/rekordbox/export.pdb` (own parser; `rekordcrate` 0.3.0 keeps its row fields private) and waveforms from the `ANLZ0000.EXT`/`.DAT` files. And the desktop library: tracks and playlists from the SQLCipher-encrypted `master.db` (`Collection::open`, via `rusqlite` with statically built SQLCipher), with a key the user supplies. Never writes either.
- `nullamp-mixxx`: read-only reader of the Mixxx library, `mixxxdb.sqlite` (a plain SQLite file, no key; opened with the same `rusqlite` build as `nullamp-rekordbox` so the two share one SQLite). `Library::open` returns the tracks (`library` joined to `track_locations`, `mixxx_deleted = 0`) and the lists in kind order: crates (`crates` + `crate_tracks`, a crate with `show = 0` skipped, sorted by name, tracks in the order they were added), playlists (`Playlists` with `hidden` 0, and the Auto DJ queue, `hidden` 1) and history sessions (`hidden` 2, named by date), entries in `PlaylistTracks.position` order. Mixxx declares numbers as text and the reverse (year, track number), so every value is read as whatever it is stored as; a BPM of 0 is unset; a track number may read "3/12". Examples: `cargo run -p nullamp-mixxx --example library -- mixxxdb.sqlite`. Tests build a synthetic database with Mixxx's tables.
- `app`: the egui UI, the playback controller, persistence and workers.

### Decisions and why

- **Rust + egui (eframe 0.37, wgpu renderer)** rather than Slint. The UI is mostly custom painting (seven-segment LCD, mix timeline, dense virtualized table), which egui does directly. Immediate mode means no binding layer between model and view. egui is MIT/Apache, whereas Slint is GPLv3, royalty-free with attribution, or commercial.
- **Own engine on symphonia 0.6 + cpal 0.18 + rubato 5 + rtrb**, not rodio. rodio 0.23 was a week-old stopgap release ahead of a rewrite, and it decodes inside the audio callback, which glitches when files sit on slow or network volumes. Our engine decodes on its own thread into a 2-second ring buffer. The callback only copies samples and applies gain. It never blocks: it uses `try_lock` and plays silence for one period on contention.
- **Tokens everywhere.** Each load gets a fresh token; positions and events carry it; the controller ignores other tokens. This is what keeps rapid skips, seeks and edits coherent.
- **Controller on the UI thread**, in eframe's `logic()` hook, which also runs while the window is hidden. Engine, workers and OS media callbacks wake it with `request_repaint`. Simpler than a separate controller thread, and frames are short.
- **Device buffer on Linux.** With `BufferSize::Default`, cpal's ALSA backend keeps two of the periods the device picks, and through the PulseAudio or PipeWire plugins that came to about 2 s: seeks and track changes were heard that long after the UI reacted (issue #6). On Linux `output.rs` now asks for 40 ms periods (clamped to the device's range, falling back to the default if refused) and logs the buffer it got. macOS and Windows keep the system default. Not yet confirmed on a Linux machine.
- **Gapless preload.** The controller tells the engine which entry comes next; the engine opens it on a loader thread and decodes into the same ring buffer. If the preload is still opening at end of track, the engine waits up to 2 s, then ends normally and the controller loads the next track.
- **File opening on short-lived loader threads**, so a cold disk or stalled network share never blocks pause, stop or a newer load. Stale results are dropped.
- **Hybrid MP3 seeking.** symphonia's accurate MP3 seek parses every frame header from the current position, and rescans from the start for backward seeks. That reads hundreds of MB for a far seek in a long mix. Forward seeks of 20 s or less stay accurate; far seeks use coarse byte-position seeking. That is exact for CBR (nearly all DJ mixes) and approximate for VBR without a seek table. Frames before the target are dropped using packet timestamps.
- **Device handling.** The stream is paused after 3 s idle (paused or stopped) so macOS can sleep. It is rebuilt on cpal `DeviceChanged`, `StreamInvalidated` or `DeviceNotAvailable` errors, and by a watchdog when the callback stops firing for 2 s. Playback resumes at the same position.
- **Output device choice.** `AudioEngine::set_output_device(Option<id>)` rebuilds the stream on that device and resumes at the same position (the same path as device recovery); `None` follows the system default. Ids are cpal `DeviceId` strings (`coreaudio:BuiltInSpeakerDevice`), saved as `output_device` in settings. A device that is gone falls back to the default (`OutputOpened.fell_back`) and is tried again on every reopen, so the choice sticks across unplugging. `request_output_devices()` enumerates on the engine thread and answers with `EngineEvent::OutputDevices`. The device list is requested on every `OutputOpened`, so the picker is already full on the first click. Each device has an `OutputKind` (`kind.rs`; on macOS CoreAudio's transport type read through objc2-core-audio, since cpal reports Unknown there; elsewhere cpal's description). The UI shows `OUT <NAME>` with a vector icon at the right end of LCD line 3; clicking it opens the picker (`deck.rs::output_label`, `output_menu`): real hardware first, virtual devices dimmed under a divider, icons from `widgets::paint_output_icon` (painted, so no font changes). `render_output_menu` in `ui_snapshots.rs` renders the open menu and an icon sheet. Tested by hand on macOS across eight devices; not yet on Windows or Linux.
- **Visualiser tap.** The callback writes each period as mono, pre-volume samples into a lock-free 8192-frame history (`output::Scope`), together with the frame index and the instant that period reaches the speaker (cpal's playback minus callback timestamp). `AudioEngine::scope(out, lead)` returns the frames ending at what is audible `lead` from now; the UI passes 12 ms for display delay. Without that alignment the picture runs a whole period plus device latency ahead of the sound. The UI side (`app/src/ui/visualizer.rs`) runs a hand-written 1024-point FFT every frame (no extra crate) and keeps its tunables (fall speed, dB floor, bar size) as constants at the top. While playing, the visualiser requests a repaint every frame, so the whole UI redraws at display refresh (up to 120 Hz) instead of the previous 33 ms tick; CPU cost not measured yet.
- **Waveform overview.** `nullamp_audio::compute_waveform` decodes the file once at its own rate and channel layout (`Decoding::open_native`, no resampling) into 10 ms blocks, then merges them into at most 2048 buckets of peak and RMS (u8 each, about 4 KB). It checks a cancel closure per packet. The app runs it on its own `nullamp-analysis` thread (a 32-minute 256 kbps MP3 takes 1.4 s in a release build), where only the newest request is kept and a newer one cancels the running decode, so skipping through a playlist costs nothing. Results are cached in `cache/waveforms/` as `<hash of store::fingerprint>.wf` (magic `NWF1`; any other format is a miss and gets recomputed), so they survive retagging and renaming. A cache hit refreshes the file's modified time at most once a day, and the thread removes entries unused for `waveform_cache::MAX_AGE` (90 days) when the app starts. The timeline draws it under the setlist boundaries and the progress tint (`deck::draw_waveform`, one mesh, one column per point, scaled to the file's loudest peak). Files on network volumes are decoded like any other; nothing detects them.
- **Tempo (BPM).** `nullamp_audio::compute_tempo` decodes about 90 s from 30% into the track (the whole track when it is under 100 s). A long file is analysed the same way, which gives the tempo of its middle, a fair answer for a mix that keeps one. While a mix with a timed setlist plays, `App::update_segment_tempo` asks for the tempo of the active track whenever its span changes: a span with room for it (at least 90 s left after cutting 10% off each end) is sampled in up to 8 windows of 30 s spread evenly over that, and the readings vote (`tempo::consensus`: readings within 1.5% form a group, the largest wins, the one nearer 120 BPM on a tie, and a group at 4/3 or 3/2 of another's tempo and nearer 120 overrules a larger one when two windows back it, because a breakdown with a dotted-eighth echo and no kick reads clearly but a third faster than the beat: "Cellar Door" of the Hodor mix read 165.4 from its middle window and is 124; no result when fewer than a third of the windows found a beat); a shorter span is the middle 70% of it (at most 90 s) as one window, so the transitions at either end stay out; the deck then shows that tempo, not the file's tags or whole-file value, and nothing while it is pending, mixes to mono, box-decimates to about 11 kHz, takes the positive spectral flux of log-compressed 512-point FFT frames every 128 samples, removes a 1 s running mean, smooths it and autocorrelates it. A comb over 60 to 200 BPM in 0.1 steps sums the autocorrelation at 1 to 8 multiples of the period (weight 1/k), with a mild lean towards 120 BPM that only breaks ties between unrelated tempos, and its best entry is the dominant period. Half and double of that fit the audio equally well (a track with weak odd beats peaks at two beats), so the member of that family nearest 120 BPM in octaves is taken and refitted within 1%; results within 0.35 of a whole number snap to it. No clear beat (steady tones, silence, confidence under 0.15) gives `None`. It takes about 0.1 s per track in a release build (`--example tempo FILE...`) and agreed within 1.5% with the BPM tags of 89 of 94 tagged files in a DJ library (the rest: four tagged above 170 BPM, which come out at half, and one file whose tag looked wrong). Slow tracks (70 to 80 BPM) come out doubled and very fast ones (170+) halved, since the family member nearest 120 wins. It runs on its own `nullamp-tempo` thread (newest request only, a newer one cancels the running analysis), so it neither waits for the waveform nor cancels it, and only once the controller has handed the track to the engine, so starting playback never waits for it. Results are cached next to the waveforms as `<hash>.bpm` (`<hash of fingerprint@start-endv2 in ms>` for a track of a mix; `v2` is the voting over windows, older single-window entries are not read) (magic `NBP1`, 12 bytes, a stored "no beat" included). A BPM already in the file's tags (`nullamp_meta::read_bpm`) skips the whole-file analysis (not that of a mix's tracks). A BPM tag of `-1` switches the tempo off for the file (`TrackInfo::bpm_off`, `nullamp_meta::read_bpm_off`): nothing is detected, the playlist cell stays empty and the deck's frame shows `---`. `Field::Bpm` is an ordinary editable inspector field: ID3v2 `TBPM` and MP4 `tmpo` hold whole numbers (a fractional value is rounded there), the freeform MP4 item, Vorbis and APE keep decimals. The deck's format line shows `128 BPM` from the tags or `~128 BPM` when detected, and the inspector offers `Detected N BPM: use it` for the playing file when the field is empty, so writing it to the tag goes through the normal safe write. The playlist has a BPM column (also in the Sort menu): `TrackInfo::bpm` holds the tag value from the scan, or a detected one with `bpm_detected` set, which is filled in when a track's whole-file tempo arrives, saved with the playlist and kept across rescans until the tags state a BPM (shown with a `~`). Cache entries are written through `<entry>.tmp` files named after the whole entry, because the waveform and the tempo of one file are written at the same time.
- **Find tracks** (October 2026, at the user's request: offline only, the user corrects the result; a Shazam scan of the whole mix was proposed and declined). `nullamp_audio::find_track_starts(path, tracks, cancel)` (`split.rs`) decodes the mix at 8 kHz mono, takes spectral peaks (1024-point FFT, hop 256, about 200 Hz to 3.1 kHz, 20 per second), pairs them into landmark hashes as Shazam does, and gives each 2 s block its set of hashes. Blocks are compared by IDF-weighted cosine over shared hashes (hashes in more than 20% of blocks ignored), then by the cosine of their rows of that matrix (which blocks they resemble; this fills in a track's parts that never repeat each other, and removed a false split inside a track). Dynamic programming over a 2D prefix sum picks the split into k stretches (each at least 60 s, less when a known k needs it) that maximises the sum of each stretch's inner similarity over its length. With `tracks` given that k is used; without it k is where the gain of one more split drops most relative to the next (gains under 20% of the largest are not considered). Measured: a 77 min mix in 7 s and 141 MB peak (the branch PoC held the whole spectrogram and used 956 MB), the 92 min "October Mix 1" in 8.4 s and 185 MB, guessing 19 of its 19 tracks; the 6-track test mix guesses 7, and with 6 given all changes are within 21 s of its cue; the 14-track "ALPTH part 27" guesses 7, so the count from a track list is what makes it usable. The spectrogram is searched for peaks in chunks of 4096 frames (`PeakFinder`, test: same peaks however the audio is fed), the matrices are f32, and the n³ profile step runs on up to 8 threads. Changes land where the next track has taken over (rekordbox cue times, logged at load, are often a minute or more earlier; the user trusts these times more). App: the setlist toolbar's "Find tracks" shows while the setlist has no times (`untimed_count`), submits `Workers::split` on its own `nullamp-split` thread (cancelled by its Cancel button and by a track change), and `on_split` gives the listed entries their starts in order as `Timing::Approximate`, or without a list adds unnamed `Provenance::Manual` entries (not `user_edited`, so a rescan may replace them); an answer for a list that changed meanwhile changes nothing. `keep_found_times` keeps those times when the comment tag is rewritten (by position when the count is unchanged, else by name). **Find missing times** (October 2026): for a list that has some times but not all (a 1001Tracklists import, where the site writes 0 for untimed tracks), the same button shows under this name when `gap_plan` finds runs of entries without a time. Each run becomes a stretch of the mix: from the start of the entry before it (0 at the head of the list) to the start of the entry after it (the end of the file at the tail), holding the run's entries plus the anchor entry, so `nullamp_audio::find_track_starts_between(path, from, to, tracks)` seeks there, decodes only that stretch and splits it into exactly that many tracks (the first start is the anchor itself). Runs with less than 30 s per track are skipped. `Workers::split_gaps` runs all gaps on the `nullamp-split` thread (`JobResult::SplitGaps`), and `on_split_gaps` gives each run's entries their starts as `Timing::Approximate`, touching only entries that still have no time. Measured on the 118 min Miss Monique "Special B'day Podcast 2020" (15 untimed tracks in 3 gaps): 8 s in all; against a hand-made reference list the found times differ by a median 9 s (14 of 15 within 20 s, worst 35 s), mostly earlier than the reference, and agree within seconds with a whole-mix split into 24 tracks (which however misplaced one track, so the anchors help). The anchors' own accuracy is the site's: they were 3 to 33 s off the audio in that mix. `split --from S [--to S] --tracks N` runs a stretch from the command line. Test: `setlist_view::tests::missing_times_are_found_between_the_known_ones`, `split::tests::finds_the_tracks_inside_a_stretch_of_a_mix`. `cargo run --release -p nullamp-audio --example split -- MIX [--tracks N]` prints the starts. Tests: `split::tests` (a made-up mix of repeated tunes, chunking, cancel), `setlist_view::tests::found_starts_time_the_list_or_make_entries`, `found_times_survive_a_rewrite_of_the_tag`, and `render_find_tracks` for pictures.
- **Key.** `Field::Key` is the `InitialKey` item (ID3 `TKEY`, Vorbis `INITIALKEY`, MP4 `----:com.apple.iTunes:initialkey`), an ordinary inspector field that is written as typed and validated by `nullamp_core::Key::parse`, which reads Camelot (`8A`), Open Key (`1m`) and musical notation (`Am`, `F# minor`, `Bb`; rekordbox and Traktor write the last, Mixed In Key the first). `TrackInfo::key` holds the parsed key and is saved as its Camelot code (an unparsable saved value is dropped, not fatal). Display follows the `camelot` setting in settings.json (`true` by default for codes like `8A`, `false` for names like `Am`); it has no UI on purpose (user preference). The deck shows no key on purpose (user preference). The playlist has a KEY column, coloured by Camelot number (`theme::camelot_color`: twelve hues in 30 degree steps from teal at 1, so wheel neighbours look alike; the letter does not change it) and "By key" in the Sort menu (along the Camelot wheel, the minor key before its relative major, untagged last). Rows of playlists saved before this have no key until "List > Rescan tags". No key detection: only what the tags state.
- **Pause, resume and volume** are atomics read by the callback, with a 15 ms gain ramp (no clicks). They take effect within one audio period.
- **Media keys** through souvlaki 0.8 (macOS MPRemoteCommandCenter and Now Playing; MPRIS via zbus on Linux; SMTC on Windows, which needs the HWND). A deduplicator drops the same transport command arriving from two different sources within 150 ms.
- **OS Now Playing for mixes** shows the constituent track as title and artist, with "Mix title, DJ" as the album, so the relationship stays visible.
- **Persistence**: JSON files with atomic writes (temp file, then rename); unreadable files are renamed `.broken` and reported. Locations come from `directories` (`~/Library/Application Support/Nullamp` etc.) or `NULLAMP_HOME`. Window geometry is stored by eframe in `window.ron`.
- **Setlist identity**: saved setlists are keyed by a content fingerprint. It hashes 64 KiB after any leading ID3v2 tag and 64 KiB before any trailing ID3v1 tag, so it survives moving, renaming and retagging. Fallback lookup is by last known path. A saved setlist wins over discovery (`workers::choose_setlist`) except an untimed one nobody edited (`Setlist::is_untouched_reference`: no `user_edited`, no `Manual` entry) while the file's own sources yield a timed list; it stays on disk and the discovery is shown as unsaved. This is what lets a cue parser fix reach a file whose cue was once saved as plain text (a rekordbox cue read as text gave 12 "no start time" problems).
- **Safe tag writing** (`nullamp_meta::write`):
  1. Validate the values.
  2. Check that size and mtime are unchanged, to catch external edits.
  3. Copy the file to a hidden temp file in the same directory.
  4. Write the tags, keeping the original ID3v2 version (lofty defaults to v2.4; we keep v2.3 files as v2.3).
  5. Mirror the edits to any ID3v1 or APE tags.
  6. Verify: tags read back as written, and duration and sample rate are unchanged.
  7. Check the original again for external edits.
  8. Optionally back up the original. For an MP3 only the tags are saved (`<ms>-<name>.mp3.id3`: magic `NLTAGBK1`, two lengths, the leading ID3v2 bytes, the trailing ID3v1 bytes) and restore splices them around the file's current audio; every other format, and an MP3 with an APE tag, gets a full copy, which restore also still accepts. The backup directory has a size budget, oldest deleted first, default 256 MB. Backups are off by default.
  9. Atomically rename the temp file over the original.

  Tests prove the audio bytes, unknown frames (PRIV, TXXX) and CHAP/CTOC chapters survive.
- **Workers**: an interactive lane (now-playing info, inspector, writes) always served before a bulk lane (playlist scans, folder expansion).
- **Themes**: dark (default), light, or follow the OS, chosen on the settings page's General tab and saved as `appearance` in settings. `ui/theme.rs` holds a `Palette` per theme; UI code calls `theme::text()`, `theme::panel()` etc., which read the palette synced from egui each frame. The LCD (`LCD_*` consts) stays dark in both themes; chrome that borrows LCD hues uses `now()`, `mix_tag()`, `key()` for legibility on light surfaces. The palette flag is process-global, so run snapshot tests with `--test-threads=1`. `render_main_window_light` writes the `*-light.png` shots.
- **App icon**: `packaging/icon.py` (standard-library Python, signed-distance drawing so any size is anti-aliased) renders a graphite plate with an LCD showing a lit mint spectrum with amber peaks above a mix timeline with an orange playhead. It feeds the macOS `.icns` (`bundle.sh` uses the committed `packaging/icon-1024.png`), the Linux icon sizes and the Windows `.res`. Linux and Windows use the `--full` variant (no shadow, plate filling about 90% instead of the macOS grid's 80%), because their docks show icons edge to edge and the macOS margin made Nullamp look smaller than its neighbours (issue #7). The window icon and the About dialog use the committed `app/assets/icon-256.png` on macOS and `app/assets/icon-256-full.png` elsewhere. After changing `icon.py`, regenerate all three PNGs: `python3 packaging/icon.py packaging/icon-1024.png`, `python3 packaging/icon.py app/assets/icon-256.png 256` and `python3 packaging/icon.py app/assets/icon-256-full.png 256 --full`.
- **Fonts**: egui 0.37's bundled fonts lack arrows, ⌘ ⌥ ⇧, ⚠ ✓ ✎ ✕ ▲▼▶▸ ◎ and similar. A 3.9 KB subset of DejaVu Sans (`app/assets/fonts/NullampSymbols.ttf`, licence beside it) is installed as a fallback for both families. To add glyphs, install fonttools in a venv and re-subset DejaVuSans.ttf 2.37 with `pyftsubset DejaVuSans.ttf --text="<all symbols>" --no-hinting --layout-features='' --output-file=NullampSymbols.ttf`.
- **Native menu (macOS)**: `ui/menu.rs` replaces winit's default menu bar through `muda` with a Nullamp menu (About, Open Config File, Services, Hide, Quit) and a Window menu. `App::install_native_menu` runs from the eframe creator in `main.rs`, not `App::new`, because muda needs the main thread and tests build the app elsewhere. Open Config File writes `settings.json` if missing, then runs `open -t` on it. The app rewrites that file on its next save, so edits made while it runs can be overwritten. About opens an egui window (`dialogs.rs`), not the system panel, so it can show the last 50 log lines kept by `logbuf.rs` on the Logs tab (a tee in front of env_logger, so it holds whatever `RUST_LOG` lets through; default is info for nullamp). `render_about`, `render_logs` and `render_updates` in `ui_snapshots.rs` render the pages. The menu bar itself is not checked by eye: screen capture is not permitted here.

- **rekordbox USB sticks** (October 2026, experimental). List > "Open rekordbox USB" reads every mounted stick (`nullamp_rekordbox::detect_mounted`: the volumes under `/Volumes` on macOS, drive letters A: to Z: on Windows, the usual removable-media folders on Linux; a folder with `PIONEER/rekordbox/export.pdb`) on a worker and makes one playlist per stick, named after the volume, with title, artist, album, duration, bitrate, BPM and key filled in from the database (opening again refreshes that playlist). The audio files are the originals under `Contents/`, played as any other file. The waveform of a file on a stick comes from rekordbox's analysis (`rekordbox::WaveformSource` on the waveform thread: finds the stick above the file, keeps its parsed database, matches files by `path_key` because the database stores "ë" composed while FAT lists it decomposed) instead of decoding the file, 150 columns per second turned into the 2048-bucket peak and RMS form, plus rekordbox's colour per bucket (red for low sounds, blue for high; `Waveform::bucket_colors`, `NowState::wave_colors`), which `deck::draw_waveform` paints far brighter than the faint LCD tint of a decoded waveform, fading out over the first and last 90 points so the time labels stay readable (`WAVE_FADE`) (`ui_snapshots::render_rekordbox_waveform`). The key and BPM rekordbox keeps in its database, not in the files, are filled into the tags' info wherever it is read (`rekordbox::Sticks::fill`, called by the scan worker and for the playing track), because otherwise the tag scan on play replaced them with nothing; tags still win where they have a value. The waveform thread also stores each rekordbox waveform in the waveform cache as `<hash of fingerprint>.rwf` (magic `NRW1`: peaks, RMS and colours) right after sending it, so the same file played from another place (the stick unplugged, a copy on the hard disk) gets rekordbox's waveform by fingerprint; with the setting off `.rwf` entries are ignored and the decoded `.wf` is used. Beside it goes `<hash>.rbi` (JSON `rekordbox::Data`: key, BPM, star rating, colour label), written whenever a file on a stick starts playing, whatever the waveform setting says; `now_playing` reads it for any file that is not on a stick and fills the key and BPM its tags lack (rating and colour are only kept; the inspector's Technical section lists every plain entry of the record under "From rekordbox", read by the `Inspect` job from the stick's library or the `.rbi` entry, so the user can check what rekordbox knows about a file: `rekordbox::Data::scalars`). Nothing reads a stick ahead of play to fill the cache. The fingerprint read of the stick file comes after the waveform is shown and covers bytes the now-playing job has just read anyway. ## 5. Library notes (versions current in October 2026)

- **symphonia 0.6.1**: new API (`AudioDecoderOptions`, `GenericAudioBufferRef`, `next_packet()` returns `Ok(None)` at the end). Decoders apply gapless trimming themselves. Accurate MP3 seeking is linear (see above). It reads ID3 CHAP frames too, but we use the `id3` crate.
- **cpal 0.18.2**: a unified `cpal::Error`/`ErrorKind`; streams no longer auto-start (call `play()`); `Stream` is now Send + Sync; CoreAudio reports `DeviceChanged` when the default output changes. On Linux enable the `pulseaudio` feature (pure Rust).
- **rubato 5**: buffers through `audioadapter`; we use `Fft` with `FixedSync::Input`, a 1024-frame chunk, output delay compensation and exact tail trimming (tested).
- **lofty 0.25**: errors are split per operation (`FileParseError`, `FileEncodingError`, etc.); `WriteOptions::use_id3v23`. The generic `Tag` view hides custom TXXX and PRIV frames but preserves them on save; we list them through the `id3` crate. `ItemKey` has no `Unknown` variant.
- **id3 1.17**: `read_from_path` also handles WAV and AIFF; remove chapters with `tag.remove("CHAP")` and `tag.remove("CTOC")`. ffmpeg writes ID3v2.3 strings with trailing NULs, so strip them for display.
- **egui / eframe 0.37**: `App::ui(&mut self, ui, frame)` plus `App::logic`; panels are `egui::Panel::top/bottom/left/right("id").show(ui, …)`; `Modal::new(Id::unique("…"))`; `Id::new` is deprecated; `ctx.all_styles_mut`; `DroppedFile` is a trait with `path()`; `ui.close()` closes menus; `ui.fonts_mut(|f| f.layout_job(job))`; `TextWrapping::truncate_at_width` for ellipsis.
- **egui_kittest 0.37** (dev-dependency with eframe, wgpu and snapshot features): `Harness::builder().with_size(…).with_pixels_per_point(2.0).wgpu().build_eframe(|cc| App::new(cc, store))`, then `step()` and `render()`. Missing glyphs panic in tests, which is how the font gap was found.
- **souvlaki 0.8.3**: uses the old `cocoa`/`objc` crates and is only lightly maintained, but it covers all three platforms. Linux uses the `use_zbus` feature. If it breaks, replace it behind `nullamp-sysmedia` (for example with `objc2-media-player`).
- **rfd 0.17**: on Linux the XDG portal is the default backend. Dialogs run with `AsyncFileDialog` on a helper thread via `pollster`, so the UI loop keeps handling media keys while a dialog is open.

## 6. Pitfalls we hit (do not repeat)

- **Disk full.** A Docker-based Linux build (rust image, cargo volume, 4.4 GB `target/linux`) filled the shared APFS container; Docker's daemon went read-only and the session could not run commands. Still left behind, and the user's to remove when they want: Docker image `nullamp-linux`, volume `nullamp-cargo`, directory `target/linux` (about 4.4 GB). The `macsplorer-*` volumes, `rust:latest` and `ubuntu:22.04` belong to another project of the user; never touch them.
- **Live window capture is not possible** here (no Screen Recording permission). Use the `ui_snapshots` test instead.
- The first seven-segment digit geometry was asymmetric and read "C:CB" instead of "0:03"; fixed. Check renders after touching `widgets.rs`.
- Cross-compiling for Linux or Windows from macOS fails on `ring` (rustls) without a C cross-toolchain.
- In tests, a second identical transport command from a *different* source within 150 ms is dropped by the deduplicator by design.
- The pause fade must limit how many samples it consumes, otherwise resuming skips ahead by up to one buffer (fixed; covered by a test).

## 7. Online sources (findings, October 2026)

Online tracklist search was removed from the app at the user's request because it rarely produced tracklists, and the per-track lookup followed. Findings to revisit later:

- **1001Tracklists** (October 2026, at the user's request, reversing the earlier "do not scrape"): Setlist → Import → "Search 1001Tracklists…" (`nullamp-tracklists`, `setlist_view::tracklist_search_modal`). The site has no API. Its search page (`POST /search/result.php` with `main_search` and `search_selection=9`) answers without any cookie; a tracklist page answers HTTP 401 unless the request carries the browser's `guid` cookie, which the user pastes into Settings > Web (`Settings::tracklists_guid`, shown as a password field). The cookie is only sent to `https://www.1001tracklists.com/tracklist/…` addresses (`fetch` refuses anything else and any value that is not alphanumeric, `-`, `_` or `.`). A normal browser user agent is sent. Requests happen only when the user searches or presses Import; the dialog starts with the playing mix's DJ and title as the query and searches at once. Tracks come from the page's `tlpItem` rows: `…_cue_seconds` (the time), `itemprop="name"` ("Artist - Title (Remix)", "ID - ID" for unknown) and `trackLabel`; they are turned into a text list and parsed by `tracklist_text::parse`, then marked `Provenance::Online { provider: "1001Tracklists" }` and `Timing::Approximate`, and merged like a paste (`apply_incoming`, the dialog's checkbox keeps user corrections). Results are ranked by `nullamp_tracklists::rank` against the mix's year (the file's date tag, else the setlist's date; also appended to the default query when missing), the words of the query found in the title, and the length of the file against the site's duration: a result of the tagged year scores 60, one a year off 15, a title word share up to 60, a length within 10% 20. A result is flagged "likely match" only when it has at least 75% of the words, the exact year (if known) and a length within 25% (if known), so another mix of the same DJ and year is not flagged. A tracklist link in the file's tags that points at 1001Tracklists gets a "Fetch it" button when the guid is set. The layout is undocumented: when it changes `parse_hits` comes up empty or `parse_tracklist` fails with "The page lists no tracks". The site writes `cue_seconds` 0 for a track nobody timed, so a 0 counts as a time only on the first track of a list that has other times (the first version put 15 of 24 tracks of one list at 0:00 and the setlist check complained about shared starts); the untimed tracks stay untimed between the timed ones. The dialog shows the best 5 results (`MAX_RESULTS`) and the mix's address is not shown in the setlist pane. Not handled: rows of tracks played together with the previous one ("w/", the class of those rows is unknown), pages beyond the first page of results. `cargo run -p nullamp-tracklists --example find -- QUERY` (with `TRACKLISTS_GUID` set) prints results and the first tracklist. Tests use small HTML fixtures, not the live site.
- **mixid.fm**: no public API; it blocks automated access (HTTP 403). Not used. The paste route works for it: copy from the page in a browser, then Setlist → Import → Paste tracklist, with the page URL kept as the source.
- **Mixcloud**: the public API finds mixes (title, DJ, date, URL, artwork), but `sections` is always empty now and descriptions rarely hold tracklists. The provider code was deleted with the `nullamp-online` crate.
- **MixesDB**: shut down, then relaunched as Mixes.wiki; no API documentation or terms found.
- **AI search engines** find *where* tracklists are, but merge sources that disagree and fill gaps. Example: for "Miss Monique – Sunset DJ Mix in Mykonos, Greece 2024" they returned two different lists (watchthedj.com with 15 tracks; the YouTube description with 16). Not usable as an automatic source.
- **Best next option**: the YouTube Data API (free key, permitted). Search for the mix and parse timestamped tracklists from the description and top comments with `nullamp_core::tracklist_text`. Many of the user's mixes are YouTube downloads. Pair it with a "Search the web" button that opens the browser with "<mix> tracklist" for paste import.
- **Identify with Shazam** (October 2026, at the user's request). The proofs of concept that led to it are on the local branch `mix-detection-poc`, not on `main`: `mixmatch` (fingerprinting a mix against a folder of the user's files), `mixsplit` (finding track changes without markers), the ShazamKit example and its signing script, and the whole-file `decode_mono` they use. The user marks where each track of a mix starts (entries from "+ At playhead", or any timed setlist) and names one track at a time with the entry's right-click item "Identify with Shazam". A first version also had an "Identify tracks" toolbar button for all entries at once; the user had it removed (they want to identify tracks individually), and the progress moved from the toolbar into the entry's row (spinner and "2/5" where the mark goes; "Cancel Shazam" in its menu). For the track, `nullamp_audio::decode_clips` decodes five 12 s clips from the middle 60% of its span (seeks, so a long mix is not decoded whole), `nullamp_shazam::signature` turns each into the signature the Shazam apps send (peaks of a 2048-point spectrogram hopped by 128 samples, in four bands, behind a CRC'd header; the format is known from SongRec and shazamio, reimplemented, not copied), and `recognise` posts it with `curl` to `amp.shazam.com/discovery/v5/.../tag/<uuid>/<uuid>` with an Android user agent. This endpoint is undocumented and using it is against Shazam's terms; the user chose it knowing that, because the alternatives cost money: ShazamKit needs an app signed by a paid Apple Developer team with the ShazamKit app service (the proof of concept on the branch got "Missing entitlements", HTTP 401, with the ad-hoc signed binary; its `crates/nullamp-audio/examples/shazam.rs` and `shazam_bundle.sh` are there for when there is a team), and AudD and ACRCloud bill after a trial. The user also chose it to be always on, without a setting. Requests go 5 s apart (`PAUSE`): 2 s got HTTP 429. On 429 the worker waits 60 s and retries once, then stops with a message; no attempt is made to get around the limit. Single clips are often wrong (on the test mix each track got one or two answers naming other songs, each such song once), so `agree` names a track only when at least 2 clips name the same Shazam key at positions in the song that fit their distance in the mix (3 s plus 10% for tempo); with five clips all 6 tracks of the test mix were named, one as another version (Shazam knows only the vocal "Troopa"), in 167 s for 30 requests (command-line run). App side: `setlist_view::identify_one` sends `Workers::identify` with one `IdentifyTrack` (the worker accepts several, unused now), which runs on its own `nullamp-identify` thread (`run_identify`), cancelled through `identify_current` by "Cancel Shazam" and by a track change (`setlist_view::reset_for_track`), and answers with `IdentifyProgress`, `Identified` and `IdentifyDone`. Only one request runs at a time; the menu item is disabled meanwhile. A named song fills an entry that is fillable (`!user_edited || is_unidentified()`, so an empty marker counts) as `Verification::Suggested` with `Provenance::Online { provider: "Shazam", url }`, and the setlist is saved; an entry the user named, one open in the editor when the answer came, and an unsure one keep their text and offer the songs at the top of the entry editor ("Use", "open"), held in `MixState::candidates` (not saved); an unsure entry shows an orange "?". The status bar says what came of it. The worker logs at info, shown on Settings > Logs: the span asked about, each clip's answer (song, position in the song, tempo and pitch skew) or "no match", failures at warn, and the verdict ("named ... (3 of 5 clips agree)", "unsure, the clips do not agree: ...", "no clip matched a song"). Tests: `nullamp-shazam` (signature header, CRC, peaks, answer parsing, voting), `mono::tests::clips_match_the_same_stretch_of_the_whole_decode`, `setlist_view::tests::identify_answers_fill_unnamed_entries_only`, and `render_identify` for pictures. Not done: matching against the user's own files first (the offline `mixmatch` example on the branch found all 6 tracks against a library folder; the user chose Shazam only for the first app version). Finding where tracks change is "Find tracks" (section 3, offline).
- **Audio recognition** (earlier notes, before Identify with Shazam): AudD's enterprise endpoint for long files, billed per 12 s of audio; ACRCloud file scanning (hearthis.at uses it, with 20 s segments). It needs a user API key and explicit consent before uploading audio (brief section 13).
- **Chromaprint fingerprints (October 2026, log only)**: `nullamp_audio::compute_fingerprint` fingerprints the first 120 s of a file with the pure Rust `rusty-chromaprint` (algorithm 2, same cap and defaults as `fpcalc`, so no external binary to bundle) and returns AcoustID's `duration` and base64 `fingerprint`. The playlist row menu "Log fingerprint" runs `Job::LogFingerprint`, which logs both plus a ready `curl` line (replace `KEY`). Nothing is sent anywhere; the user is testing AcoustID, AudD and ACRCloud by hand first. Chromaprint targets whole-file matching, so snippets recorded from a speaker will match poorly. `cargo run --release -p nullamp-audio --example fingerprint FILE` prints the same values.
- **Removed: MusicBrainz and Cover Art Archive lookup** (October 2026, at the user's request: too error prone and complex for how often it was used). It lived in the Inspector ("Find metadata online") and as "Look up…" in the setlist entry editor, in the `nullamp-online` crate, which is deleted along with the status bar toggle and the `online_lookups` setting. The exact-phrase Lucene query (`recording:"title" AND artist:"artist"`) missed every title with a remix suffix such as "(Club Edit)" or "(Original Mix)". A live comparison found that iTunes Search and Deezer (both free, no key) matched those titles; iTunes was best on suffixes and had high-res artwork but its terms target promoting Apple content, and Deezer needs the plain `artist title` query (its field syntax returned nothing). All three return wrong tracks for obscure titles, so any revival needs an artist-similarity and duration check. Discogs would cover underground releases but needs a user token. `Provenance::Online` and `SetlistEntry::artwork_url` remain in `nullamp-core` only so older saved setlists still load.

- **Artwork of the tracks inside a mix** (October 2026, at the user's request; artwork only, nothing else online). When a track of a mix becomes active for the first time while its file plays, `App::update_entry_art` sends its artist and title to the worker thread named `nullamp-online` (one thread, answers in order, so seeking across tracks fetches each once). The thread checks `entry_art` (cache under `cache/artwork/tracks`, keyed by the normalized artist and title so the same track in another mix shares it; found covers are kept 30 days as the image file, which also feeds the OS Now Playing overlay, misses 7 days as a `.none` marker holding `nullamp_artwork::MATCHER_VERSION`, so raising that after a matching fix retries earlier misses; expired entries are pruned at startup), else calls `nullamp_artwork::find` and `download`. Network failures are not cached on disk; in memory the track is marked `EntryCover::Failed` and asked again after 60 seconds or when it next becomes active (the first version dropped the marker and asked again on every frame, which while offline meant a loop of `curl` runs), and the deck shows the file's cover meanwhile. While looking, the deck and the Now Playing overlay show the file's cover. When nothing was found the deck shows a generated placeholder (`app/src/placeholder_art.rs`: a retro landscape with a slit sun, ridges, perspective grid, ring and moon, drawn from FNV-1a of the `entry_art::key`, so a track looks the same in every mix and run; it is drawn on each request, not cached, so generator changes reach old misses), and the Now Playing overlay keeps the file's cover because a placeholder has no image file. Beatport was tried for tracks the services lack and is not usable: the site sits behind a Cloudflare challenge and the API needs OAuth. Entries without an artist or title, and "ID - ID" entries, are not looked up. `Settings::online_artwork` (settings.json only, on by default) switches it off. Tested on a rekordbox recording of 10 tracks: Deezer found the right release for all 10, iTunes for 9 (it missed one collaboration and picked a compilation for another). Deezer often names only the first artist of a collaboration, hence the subset rule. rekordbox separates artists with `;` ("Donnie; Yung Felix"), which the first version missed. Still to come, when the user asks: covers stored in MP3 chapter frames (CHAP with APIC), covers the user assigns per entry, and the source files a rekordbox cue sheet names per track (`FILE` inside `TRACK`).

- **"Find online" in the inspector's Artwork section** (October 2026, at the user's request): looks up a cover for the one inspected file from the artist and title as currently typed in the form, through the same `nullamp_artwork::find` and `download`, on the `nullamp-online` thread (`Workers::request_track_cover`, answered with `JobResult::TrackCover`). The image is added to the list as `ArtworkKind::Other`, never as front cover, and is only written when the user saves; "Set as front cover" works as for any image. Nothing is cached on disk and a byte-identical image already in the list is not added twice. Disabled for batches, without artist or title, and when `Settings::online_artwork` is off.

## 9. Known limitations

- Far seeks in VBR MP3s without a seek table are approximate.
- The setlist panel follows the playing file only; you cannot edit the setlist of a file that isn't playing.
- Batch editing is capped at 500 files.
- Writing tags to the file that is playing works on macOS and Linux (the engine keeps the old inode open). On Windows the rename would fail and is reported as an error.
- Approximate timestamps from pasted lists are shown with "≈" and dashed timeline boundaries. Use "→ playhead" while listening to correct them; that marks them exact.
